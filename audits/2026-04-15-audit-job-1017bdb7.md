## Hallazgos

### Hallazgo 1 — `getDominantColor` mide el patrón floral, no el color de la sábana
- **Evidencia (caso real)**: pipeline_log: `swatch_rgb={r:130,g:106,b:137}` (= lila/morado), pero el archivo del swatch "Gris" es un juego de sábanas BLANCO con flores moradas + amarillo en bordes. El verdadero color del producto es BLANCO. El RGB(130,106,137) es el promedio de los pétalos lila aislados.
- **Estado actual**: `src/lib/image-processing.ts:38-39`
  ```
  if (brightness < 40 || brightness > 240) continue;  // descarta blancos
  if (saturation < 0.25) continue;                     // descarta grises/blancos
  ```
  Este filtro está diseñado para ignorar el fondo blanco de un swatch macro tipo "tela cerca", pero cuando el swatch es una FOTO COMPLETA DE PRODUCTO (sábana blanca con flores), el filtro descarta toda la tela base y deja sólo los pétalos. El "color dominante" termina siendo el color del PATRÓN, no del PRODUCTO.
- **Gap**: la función no distingue "swatch macro de tela" vs "swatch lifestyle de producto entero". Para sabanas (`crop_swatch: false` en `category-strategy.ts:186`) no hay crop previo que aísle la tela, así que `computeSwatchOutputDeltaE` ve la imagen entera y mide los pétalos.
- **Cascada**: con swatch_rgb pintado del pétalo, Gemini genera correctamente sábanas blancas (output_rgb = beige cálido del banner inferior infografía + sábanas blancas) y el Delta-E entre "lila falso" vs "beige real" da 30+ → reject infinito.
- **Propuesta**:
  - **A (cirugía mínima, P0)**: `computeSwatchOutputDeltaE` debe usar **el color base** del swatch, no el dominante de los pétalos. Implementar `getBaseFabricColor()` que devuelva el color de la mayor región conexa de píxeles brillantes y poco saturados (lo opuesto al filtro actual). Si la mayor banda de píxeles del swatch es blanco/gris claro, ESE es el color base.
  - **B (defensa adicional, P0)**: cuando `swatch.dominant_color_hex IS NOT NULL`, **preferir el hex** sobre el resultado de `getDominantColor` (Vicente o un análisis previo ya validó el color). Ahora ese campo no se usa para Delta-E (`process-next:1058-1067` sólo le pasa el buffer al function).
  - **C (escape hatch, P1)**: si `swatch.color_description` matchea un nombre conocido (`colorNameToHex` ya existe en `image-processing.ts:187`), comparar contra ese hex en vez de la imagen. "Gris" mapearía a un hex gris y el verifier no compararía contra los pétalos.
- **Prioridad**: ALTA
- **Impacto esperado**: desbloquea ESTE job. Elimina la familia de "Delta-E loop infinito en swatches con patrón visible".

### Hallazgo 3 — `replaceNote` inyecta wording de "cubrecama" en prompts de sabanas
- **Evidencia (caso real)**: `prompt_text` del job tiene literalmente:
  > "El cuerpo del **cubrecama** Y las fundas deben tener AMBOS el mismo patrón uniforme de Imagen 2"
  
  Pero `category=sabanas`. Las sabanas no son cubrecamas y la regla del bloque ROBOLA del prompt original (`category-strategy.ts:188-220` para sabanas) habla de "fitted sheet", "pillowcases", "sheet set" — un dominio diferente.
- **Estado actual**: `src/lib/category-strategy.ts:899-908` — `replaceNote` está hardcoded:

  Es un string template que se concatena en `buildEditPrompt` para CUALQUIER categoría cuando `patternsDiffer=true`. No usa `strategy.label` ni `strategy.prompt.product_context`.
- **Gap**: prompt mezcla terminologías. Gemini recibe "cuerpo del cubrecama" + "Sheets are FLAT, thin fabric — DO NOT add volume" (de la sección sabanas del strategy) en el mismo prompt. - **Propuesta**: parametrizar el `replaceNote`:

- **Prioridad**: MEDIA (no es la causa raíz, pero ensucia el prompt y reduce QA en una familia entera de jobs)
- **Impacto esperado**: prompts coherentes por categoría cuando se activa el `replaceNote`.

### Hallazgo 4 — Pattern comparator no escala a `from_scratch` para sabanas con patrón complejo (no hay rama paralela a quilts)
- **Evidencia (rebatiendo parcialmente diagnóstico #2 del usuario)**: pipeline_log muestra `PATTERN_COMPARED detail=false` (patterns differ) en attempts 1 y 2, y `effective_mode=edit` quedó. El user dice "en quilts hay auto_switch quilts_edit_to_reference" — **falso en el código actual**. Lee `category-strategy.ts:62-66`:
  > "Stay in edit mode on verifier retries — reference mode loses the hero's exact composition."
  
  Los quilts también se quedan en edit (`retry_escalation: 'edit'`). Y en `process-next:579-587`, el comentario explícito dice:
  > "patterns DIFFERENT → stay in the strategy default (edit for quilts). The previous logic pre-emptively escalated quilts to reference/from_scratch on pattern mismatch, but that caused reference mode to invent accent props."
  
  Es decir, la rama de `patterns_differ_quilts_edit_to_reference` **fue removida intencionalmente** porque inventaba almohadas. Hoy nadie escala automáticamente a reference cuando `patternsDiffer=true`, ni quilts ni sabanas.
- **Estado actual**: `process-next:573-591` corre `arePatternsSimlar`, pero la única acción auto es `similar=true && mode=='reference' → mode='edit'` (downgrade). Nunca el upgrade. Para sabanas (`generation_mode='edit'`, `retry_escalation='edit'`), la salida del comparator no afecta el modo. Sólo activa el `replaceNote` adentro de `buildEditPrompt`.
- **Gap real**: no es que falte la rama "auto-switch para sabanas" — es que la decisión de "rebuild from scratch cuando patrones difieren mucho" fue eliminada para todos. Este caso muestra que para HEROS LISOS + SWATCH FLORAL, edit mode es estructuralmente incapaz: Gemini no puede pintar flores donde no había nada. Termina preservando el hero blanco intacto.
- **Propuesta**:
  - **Opción A (P1)**: re-introducir un escalamiento opt-in: si `patternsDiffer===true` Y la categoría está en `{sabanas, cubrecamas, plumones}` Y `attempt >= 2`, **escalar a `reference`** (no `from_scratch`). El objetivo no es regenerar la escena entera (eso inventa props) sino darle a Gemini permiso explícito de pintar la tela completa con el patrón del swatch usando la composición del hero como guía. Como el problema reportado del pasado (reference inventa almohadas) era en quilts, podemos excluir quilts de esta heurística.
  - **Opción B (P1)**: introducir un check en el verifier que detecte específicamente "el hero pasó intacto" comparando hash perceptual hero↔output. Si `dHash(hero, output) < 5%`, **forzar reference en el siguiente retry** sin importar la categoría. Este check captura "Gemini ignoró el swatch" como modo de fallo, ortogonal a Delta-E.
- **Prioridad**: MEDIA
- **Impacto esperado**: rescata jobs donde edit mode es estructuralmente imposible. No rompe los casos quilts donde edit funciona.

### Hallazgo 5 — `replaceNote` discard de qaFeedback bloquea el feedback de Delta-E
- **Evidencia**: pipeline_log muestra que attempts 1 y 2 reciben `[Delta-E 31.4]` y `[Delta-E 30.2]` como qaFeedback, pero ese feedback **nunca llega a Gemini** porque:
  - `category-strategy.ts:892`: `const effectiveQaFeedback = patternsDiffer ? null : qaFeedback;`
  - En este caso `patternsDiffer=true` → `effectiveQaFeedback = null` → no se inyecta `INTENTO ANTERIOR FALLÓ` al prompt.
- **Estado actual**: el discard fue introducido por el commit `4e34e4c` ("discard INTENTO ANTERIOR FALLÓ when patterns differ — poison loop"). El razonamiento original era válido (el verifier 2.5 Pro decía "pattern doesn't match" y Gemini lo leía como "preserva el hero"). Pero el filtro **descarta TODO qaFeedback**, incluyendo el de Delta-E que no es ambiguo.
- **Gap**: el discard no diferencia entre fuentes de feedback. `[Verifier 2.5 Pro]` puede ser veneno, pero `[Delta-E 30.2] Color drift detected` es información concreta sobre desalineación de color que Gemini SÍ puede usar.
- **Propuesta**: filtrar por prefijo, no por flag binario:
  ```ts
  // category-strategy.ts:892
  const isVerifierFeedback = qaFeedback?.startsWith('[Verifier');
  const effectiveQaFeedback = (patternsDiffer && isVerifierFeedback) ? null : qaFeedback;
  ```
  Conserva la protección anti-poison pero deja pasar Delta-E feedback.
- **Prioridad**: MEDIA
- **Impacto esperado**: en cualquier loop "patterns differ + Delta-E reject", Gemini al menos sabe que el color va mal y tiene una pista accionable.

### Hallazgo 9 — `swatchColorDescription="Gris"` se loguea en metadata pero NO se inyecta al prompt del editor
- **Evidencia**: `prompt_metadata.swatch_color="Gris"`. El usuario teme que el prompt diga literalmente "color Gris" contradiciendo el swatch (que es blanco floral). Verifiqué el `prompt_text` del job: **no contiene la palabra "Gris"**. Sólo dice "el color/patrón/textura de Imagen 2".

Sólo `formatColorAnchor` (líneas 850-869) lo usaría, y `formatColorAnchor` **no se llama desde `buildEditPrompt`** — sólo desde `buildReferencePrompt`/`buildFromScratchPrompt` (no auditado en este job, pero verificable por grep).
- **Gap parcial**: el riesgo está mitigado porque edit mode no inyecta el nombre de color al prompt. PERO: si en el futuro se cambia a `reference`/`from_scratch` para sabanas, `colorDescription="Gris"` (que es WRONG para el swatch real) se inyectaría en el prompt como ancla de color y empujaría a Gemini a generar gris en vez de blanco floral. Es una bomba de tiempo.
- **Propuesta**: cuando `swatch.color_description.length <= 100` y existe `swatch.dominant_color_hex`, **NO usar el name como `colorDescription`** — usar el hex. Si tampoco hay hex, dejar `null` (que el prompt no inyecte ancla de color). Hoy `process-next:467` hace fallback `if (!swatchColorDescription) swatchColorDescription = job.swatch.name`, lo cual agrava el problema con swatches mal nombrados.
- **Prioridad**: MEDIA (preventiva — no causó este job, pero causaría el siguiente)
- **Impacto esperado**: bloquea la propagación de nombres de swatch engañosos a futuros prompts.

### Hallazgo 10 — Sabanas marca `crop_swatch: false` aun cuando los swatches son fotos full-product
- **Evidencia**: `category-strategy.ts:186`: `preprocessing: { crop_swatch: false, flatten_hero: false }`. Resultado en este caso: a Gemini le llega el JPG ENTERO del swatch (sábanas blancas con flores moradas en cama, presumiblemente con pillows en escena), no un crop limpio de la tela. La verificación Delta-E también recibe el JPG entero. Esto enchufa directo al Hallazgo 1.
- **Estado actual**: la decisión es deliberada (probablemente para preservar la diferencia entre patrón de pillowcases y patrón de fitted sheet, que el strategy de sabanas explica en su `what_to_change`). Pero significa que el dominant color medido siempre estará dominado por el background lifestyle del swatch.
- **Gap**: para sabanas y otras categorías con swatches lifestyle, el preprocesamiento sale "todo o nada". O preservás todos los patrones del swatch (sin crop), o pierdes la distinción pillows/sheet (con crop). No hay una vía intermedia.
- **Propuesta**: añadir `crop_for_color_check_only: true` a la strategy. Esto haría:
  - El swatch que se manda a Gemini se queda SIN crop (preserva pillows + sheet patterns).
  - El swatch que se manda a `computeSwatchOutputDeltaE` se crop con `cropSwatchToFabric` (color limpio).
  Implementación: en `process-next:1058`, derivar `swatchBufForDrift` siempre crop-to-fabric independientemente de `strategy.preprocessing.crop_swatch`.
- **Prioridad**: MEDIA
